# Нагрузочный тест (спринт 7)

Скрипт `loadtest/load.py` создаёт N объектов с заказчиком и прорабом (вход по ссылке, ключ устройства) и
запускает C виртуальных пользователей: 70 % открывают кабинет заказчика (объект, этапы, лента, заказы
материалов — 4 запроса сразу), 20 % — прораб снимает фото (код съёмки + загрузка 1280×960 с подписью
устройства), 10 % — менеджер закупок смотрит заказы и заявки. Между действиями пауза 0,5–1,5 с.

Запуск на локальном стенде (нужен `OTP_DEBUG=true` и `RATE_LIMIT_PER_MINUTE=0` в `.env`, из корня репозитория):

```bash
docker compose up -d
OBJECTS=10 USERS=50 SECONDS=60 python loadtest/load.py
```

## Результаты, 27.11.2026

Стенд: одна машина 4 vCPU, на ней же база, Redis и сам генератор нагрузки. Backend — 2 процесса uvicorn.

| Сценарий | Запросов в секунду | Ошибок | p50 | p95 | p99 |
|---|---|---|---|---|---|
| Масштаб пилота: 15 одновременно активных | 49 | 0 | 11–36 мс | 26–59 мс | до 0,5 с |
| С запасом: 50 одновременно активных, до исправлений | 105 | 0 | 115–196 мс | 1,1–1,5 с | до 3,3 с |
| С запасом: 50 одновременно активных, после исправлений | 128 | 0 | 38–91 мс | 0,5–1,1 с | до 3 с |

На пилоте 8+ объектов одновременно активных людей будет меньше 15, запас — больше чем в 3 раза.
Хвост p99 при 50 пользователях упирается в процессор общей машины (генератор нагрузки работает там же).

## Что исправлено по итогам

- Разбор фото (проверка формата и перцептивный хэш) вынесен в отдельный поток: раньше он на 20–50 мс
  останавливал все остальные запросы того же процесса.
- Пул соединений с базой увеличен до 10 + 10 на процесс (было 5 + 10): при пиковой нагрузке запросы
  стояли в очереди за соединением.
- Uvicorn держит соединение 130 с (было 5): прокси и клиенты переиспользовали соединение, которое сервер
  уже закрыл, — отсюда были редкие обрывы «Server disconnected».

## Что отложено

- Поиск похожих фото перебирает все снимки (`bit_count` по таблице). На пилоте это десятки тысяч строк,
  миллисекунды. Для тысяч объектов — индекс по частям хэша (спринт после Gate 1).
